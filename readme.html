Palio di Siena — Setup Guide

Publishing the dashboard as an installable app

An installable web app covering the Palio di Siena: every contrada, jockey, horse and drappellone from 1633 to today, plus the field for the next race. Data comes from ilpalio.org, the non-profit archive curated by Orlando Papei and authorised by the Consorzio per la Tutela del Palio di Siena. This is an unofficial personal project.

2Putting it on GitHub Pages

You'll do this once. Afterwards, updating is just replacing index.html. Allow about ten minutes.

Create the repository

  1. Go to github.com/new (sign in first).
  2. Repository name: palio — or anything you like; it becomes part of the web address.
  3. Set it to Public. GitHub Pages needs public on a free account.
  4. Leave every checkbox unticked — no README, no .gitignore. This folder already has what it needs.
  5. Click Create repository.

Upload the files

  1. On the empty repository page, click uploading an existing file.
  2. Open this palio-pwa folder on your Mac and drag everything inside it onto the browser window — index.html, manifest.webmanifest, sw.js, readme.html, and the icons folder.
  3. Scroll down and click Commit changes.
Drag the contents, not the folder

index.html must sit at the top level of the repository. If it ends up inside a palio-pwa sub-folder, the site address won't find it.

The hidden file

.nojekyll starts with a dot, so Finder hides it. Press ⌘ Shift . in Finder to show hidden files, drag it across too, then press the same keys again to re-hide them.

Turn on Pages

  1. In the repository, click Settings (top right).
  2. In the left sidebar, click Pages.
  3. Under Source, choose Deploy from a branch.
  4. Set the branch to main and the folder to / (root), then click Save.
  5. Wait a minute or two and refresh. GitHub shows the address at the top: 
    https://YOUR-USERNAME.github.io/palio/
    Replace YOUR-USERNAME with your GitHub username. That's your app.
Why GitHub and not just the file on your Mac?

Service workers — the thing that makes an app installable and able to run offline — only work over https. Opening the .html from your hard drive skips that part. Everything else still works; you just don't get the install button.

3Installing it on a device

iPhone or iPad

Open the address in Safari — on iOS only Safari can install web apps. Tap Share, scroll down, tap Add to Home Screen. It gets an icon and opens without browser chrome, like any other app.

Mac — Chrome or Edge

Open the address, then click the small install icon at the right of the address bar, or use ⋮ → Cast, save and share → Install page as app.

Android

Chrome usually offers "Add to home screen" by itself. If not: ⋮ → Add to Home screen.

4Updating it later

When the dashboard is rebuilt after a new Palio:

The easy way — double-click publish.command

There's a publish.command file in this folder. Double-click it in Finder and it shows you what has changed, asks you to confirm, and sends everything to GitHub. The live site updates a minute later.

It uses whichever GitHub sign-in is already on your Mac, so it never asks you for a password or token — and neither will I. That stays between you, your Mac's keychain and GitHub.

First time only — sign this Mac in to GitHub

Pick whichever suits you:

  • GitHub Desktop (easiest) — install from desktop.github.com, sign in, add this folder as a local repository.
  • GitHub CLI — brew install gh then gh auth login, which signs you in through your browser.
  • Nothing extra — just push once and GitHub will prompt. The "password" it wants is a personal access token, not your account password: Settings → Developer settings → Personal access tokens. macOS keeps it in the keychain afterwards.

Then connect this folder to your repository, once:

git init -b main
git remote add origin https://github.com/YOUR-USERNAME/palio.git
git add -A
git commit -m "First publish"
git push -u origin main

Or by hand, through the website

  1. On the repository's main page, click Add file → Upload files.
  2. Drag the new index.html and sw.js in. GitHub replaces the old ones.
  3. Click Commit changes. The live site updates within a minute.

How the installed app picks up a new version

The app deliberately runs from its own saved copy. That's what makes it open instantly and work with no connection — but it also means it will not quietly replace itself while you're reading. Nothing changes until you ask.

At the top of the dashboard there's a line that reads "Installed copy — updates are only fetched when you ask" with a Check for updates button beside it. That button is the whole mechanism:

  • When the app opens it quietly asks GitHub whether a newer version exists. If one does, the line changes to "A new version is available" and the button becomes Update now. Nothing is applied yet.
  • Pressing it throws away the saved copy of the app, activates the new version and reloads. Takes a second or two.
  • You can press it any time, even when no update is waiting — it will always go and check.
Your banners are kept

Updating clears the app files but deliberately leaves the drappellone photographs alone. Those never change once published, so re-downloading them would cost you time for nothing.

The version number now looks after itself

Browsers only treat an upload as genuinely new when the CACHE_VERSION line in sw.js changes — and remembering to edit it by hand is exactly the sort of thing that gets forgotten.

So it's no longer done by hand. The build script fingerprints the app and writes that fingerprint in for you:

const CACHE_VERSION = 'palio-e794e137';

Identical content keeps its version; any change at all produces a new one. Nothing for you to remember.

5What works offline

  • The dashboard itself — every tab, chart, table and pop-up. All the data is inside index.html, so nothing needs fetching.
  • Drappellone photographs you've already viewed. These live on ilpalio.org and are linked rather than copied; the service worker saves each one the first time you see it. Banners you've never opened won't appear until you're back online.
Why the banners aren't bundled in

Copying all 537 into the app would add roughly 22 MB and make it slow to open, so they're linked instead. The side benefit is that new banners appear on their own as soon as ilpalio.org posts them, with no update needed here.

They are served from ilpalio.org — their bandwidth, and a public site draws more of it than a file on your own machine. It's a small archive of small thumbnails and this is a personal project, so the load is negligible. If you'd rather not lean on someone else's server at all, the alternative is to copy a subset in; the last 25 years is about 1.5 MB, which is perfectly manageable.
